2026-10-14 - Double-sigmoid in the reranker CONFIRMED and fixed (Claude Code). Evidence that triggered this: the debug trace's `reranker.top5_raw_logits` showed 0.99987 feeding a final score of 0.731 (= sigmoid(1.0)), and the 2026-10-13 off-topic smoke-test query scored confidence exactly 50 (= sigmoid(0)*100) — both are the signature of applying sigmoid twice.
  - Root cause, confirmed by reading the installed package and by a local CPU-only experiment (`lexai/backend/scratch/rerank_check.py`, not committed, no network calls beyond the already-cached model weights, never touched the running server): installed `sentence-transformers==6.1.0`, `CrossEncoder.get_default_activation_fn()` (cross_encoder/model.py) returns `nn.Sigmoid()` whenever `num_labels == 1`, which `bge-reranker-base` is (`reranker.num_labels == 1` confirmed at runtime). `CrossEncoder.predict()` applies that activation by default, so `self.reranker.predict(pairs)` was already returning a 0..1 probability, not a logit, despite the inline comment `# raw logits, NOT 0..1`. `_rerank()` then called `_sigmoid()` on that already-sigmoided value — sigmoid applied twice.
  - Measured on the three test pairs (RERANK_MODEL = BAAI/bge-reranker-base, the hardcoded engine default — not read from .env): relevant pair raw logit 7.902067, `predict()` default 0.999630 (== sigmoid(7.902067)), engine's old double-sigmoid score sigmoid(0.999630) = 0.730986 -> confidence 73. Both irrelevant pairs (FIFA 2018 winner; capital of France) scored raw logit ≈ -10.19, `predict()` default ≈ 0.000037, old double-sigmoid score ≈ 0.500009 -> confidence 50 for both — reproducing the exact 73/50 pattern from the smoke test and debug trace. Because sigmoid(sigmoid(x)) for any real x lands in roughly [0.5, 0.731] (sigmoid's own range is (0,1), and sigmoid of anything in (0,1) is bounded between sigmoid(0)=0.5 and sigmoid(1)=0.731), the old code could never produce a score below ~0.5, so a 0.30 confidence-gate threshold could structurally never refuse anything — this fully explains the 2026-10-13 OPEN ISSUE (confidence 50, refused=false on an off-topic query) and is the same mechanism entry 2026-10-14 ("Diagnostic tracing") already predicted from code alone before this was run.
  - Fix, in `lexai_engine.py` only: `_rerank()` now calls `self.reranker.predict(pairs, activation_fn=torch.nn.Identity())` to get the true raw logit, then applies `_sigmoid()` exactly once (unchanged). Added `import torch` (already an indirect dependency via sentence-transformers/torch itself, not a new package). `debug_info["reranker"]["top5_raw_logits"]` is now a true logit list instead of an already-sigmoided value mislabeled as a logit. No change to `_sigmoid()`, `CONF_THRESHOLD` (still 0.30), prompts, models, `max_tokens`, or any retrieval/RRF logic. Verified: all files outside `lexai_engine.py`/`PROJECT_LOG.md`/`scratch/` hash-identical before and after (SHA-256 list in `lexai/backend/scratch/baseline_hashes_p4.txt`), `ast.parse` clean, `git status --short` shows only `lexai_engine.py` modified, diff is 2 lines added (one import, one comment block) plus one changed call.

2026-10-15 - LLM resilience: per-call timeout + NVIDIA -> Groq failover (Claude Code). Evidence that motivated this (reported stalls on the live NVIDIA free endpoint, not reproduced this session): generate took 175s, verify took 320s, and condense took 209s for calls of roughly 80 completion tokens, versus ~0.9s for a bare call — i.e. intermittent multi-minute stalls, not a model-size-driven slowdown. The OpenAI SDK's own defaults (timeout=600s, max_retries=2) do nothing to shorten a stall like that, they just retry it up to 3 times. Separately, Groq retired the configured fallback model `llama-3.1-8b-instant` on 2026-08-16; its stated replacement is `openai/gpt-oss-20b`. Groq's documented limits for `openai/gpt-oss-20b` (plan tier — free vs. developer — unclear from what was checked): 30 requests/min, 1,000 requests/day, 8,000 tokens/min, 200,000 tokens/day.
  - Implemented in a new module, `lexai/backend/llm_client.py` (no model loading, so importable and testable with zero network calls): a `LLMClient` class that builds per-provider OpenAI-compatible clients with `timeout=LLM_TIMEOUT_S` (env, default 30s, float) and `max_retries=0` (failover replaces the SDK's own retries). `complete()` tries the primary provider (`LLM_PROVIDER`, default nvidia, model overridable by `LLM_MODEL` as before); on `openai.APITimeoutError`, `APIConnectionError`, `RateLimitError`, or any other `APIStatusError` (5xx etc.), it tries the fallback provider (`LLM_FALLBACK_PROVIDER`, default groq, model overridable by `LLM_FALLBACK_MODEL`) once, but only if that provider's own API-key env var is non-empty; if the fallback also fails, or isn't configured/available, it raises a new `LLMUnavailableError` whose message contains no key material and no URLs. A `BadRequestError` (400) is treated as a bug in our own request and is re-raised immediately without attempting a failover, so it is never silently masked. Every attempt (successful or not) is appended to `self.attempts` — provider, model, purpose, attempt number, outcome (`"ok"` / `"timeout"` / `"error:<ExceptionClassName>"`), duration_ms, and prompt/completion tokens + finish_reason when available — and provider switches are logged at `WARNING` level via the `logging` module, never including key values.
  - `lexai_engine.py`: `self.llm` / `self.llm_model` / the old `_PROVIDERS` dict and `LLM_PROVIDER` constant are gone from this file; `__init__` now builds `self.llm_client = LLMClient()` and `_ask_llm()` delegates to `self.llm_client.complete(...)`, extending the caller's `calls_log` with whatever `LLMClient.attempts` recorded for that call (so `dbg["llm_calls"]` entries gained `provider` and `outcome` fields; `purpose`/`model`/`duration_ms`/`prompt_tokens`/`completion_tokens`/`finish_reason` are unchanged). The single `_PROVIDERS` table (with the corrected Groq default model `openai/gpt-oss-20b`) now lives only in `llm_client.py`, not duplicated in both files — deliberate, since `llm_client.py` has to stay importable without pulling in `lexai_engine.py`'s heavy model-loading imports (torch/sentence-transformers/chromadb) for it to be unit-testable offline. No prompts, thresholds, `max_tokens`, retrieval, RRF, or reranker logic were touched. `api.py`: `/query` now catches `LLMUnavailableError` and returns HTTP 503 with detail "The language model service is temporarily unavailable.
